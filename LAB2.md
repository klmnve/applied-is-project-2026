# Лабораторная работа №2

**Тема:** проектирование реляционной базы данных и создание ORM-моделей в ИС учета успеваемости студентов.

## Цель и результат

ER-диаграмма из ЛР №1 перенесена в SQLModel. Создаются четыре таблицы SQLite: `teachers`, `students`, `subjects`, `grades`. Во всех таблицах есть целочисленный первичный ключ `id`.

| Внешний ключ | Ссылка | Кардинальность |
| --- | --- | --- |
| `subjects.teacher_id` | `teachers.id` | Один преподаватель — много предметов |
| `grades.student_id` | `students.id` | Один студент — много оценок |
| `grades.subject_id` | `subjects.id` | Один предмет — много оценок |

Обратные объектные связи заданы через `Relationship(back_populates=...)`: `teacher.subjects` ↔ `subject.teacher`, `student.grades` ↔ `grade.student`, `subject.grades` ↔ `grade.subject`. Такой способ объявления описан в [документации SQLModel](https://sqlmodel.tiangolo.com/tutorial/relationship-attributes/define-relationships-attributes/).

Студенты и предметы образуют связь «многие-ко-многим» через таблицу `grades`, которая содержит дополнительное поле `grade`. Для чтения предусмотрены `student.subjects` и `subject.students` с `link_model=Grade` и `viewonly=True`; для записи используется объект `Grade`. Это предотвращает создание связи без обязательной оценки. Основа подхода — [связующая модель SQLModel](https://sqlmodel.tiangolo.com/tutorial/many-to-many/create-models-with-link/).

Названия таблиц в SQL записаны строчными буквами, как принято в проекте; состав полей соответствует ER-диаграмме. Дополнительно выбрана шкала оценок 0–100: она проверяется ограничением `CHECK` в БД и описана в `Field(ge=0, le=100)`. Это принятое для тестового примера допущение, поскольку шкала на диаграмме не указана. Уникальность пары студент–предмет не вводится: у студента может быть несколько оценок по одному предмету.

## Подключение и инициализация

`backend/db.py` создает движок SQLite с `echo=True`. Путь `database.db` вычисляется относительно корня проекта, поэтому не зависит от текущей рабочей папки процесса. Функция `init_db()` вызывает `SQLModel.metadata.create_all()` после импорта всех моделей.

Для каждого подключения включается `PRAGMA foreign_keys=ON`: иначе SQLite по умолчанию может не проверять объявленные внешние ключи. Это поведение описано в [документации SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#foreign-key-support).

Данные старой базы `backend/db.sqlite3` не удаляются и автоматически не переносятся. Рабочая база ЛР №2 — `database.db` в корне репозитория. Создание таблиц не выполняет миграции существующих столбцов.

## Тестовые данные

`seed.py` сначала вызывает `init_db()`, затем добавляет недостающие записи через `Session` и фиксирует их одной транзакцией:

| Таблица | Число записей в новой БД |
| --- | ---: |
| `teachers` | 3 |
| `students` | 3 |
| `subjects` | 3 |
| `grades` | 5 |

Повторный запуск ищет совпадающие тестовые записи и не добавляет их повторно. Имеющиеся пользовательские записи не очищаются. Искусственные ФИО и оценки предназначены только для разработки.

Пример работы с объектной связью после запуска `python seed.py`:

```python
from sqlmodel import Session, select
from backend.db import engine
from backend.models import Student

with Session(engine) as session:
    student = session.exec(select(Student).order_by(Student.id)).first()
    for result in student.grades:
        print(student.full_name, result.subject.name, result.grade)
```

Связанные объекты здесь читаются внутри открытой сессии, поскольку ORM может загружать их отдельными запросами.

## Проверка

Команда: `python -m unittest discover -s tests -v`.

Проверяются:

1. Названия четырех таблиц, состав полей, первичные ключи и все три внешних ключа.
2. Количество тестовых записей, неизменность количества после повторного запуска и отсутствие нарушений FK.
3. Двухсторонние связи 1:N и M:N, запись через объекты, несколько оценок по одному предмету.
4. Отклонение ссылок на несуществующего преподавателя, студента или предмет.
5. Отклонение оценок вне диапазона 0–100 самой базой данных.
6. Обязательность полей на уровне БД.
7. Запуск FastAPI, доступность `GET /` и OpenAPI.

Каждый тест использует отдельную временную SQLite-базу, которая удаляется после проверки. Реальная `database.db` не очищается.

## Ответы на контрольные вопросы

### 1. Что такое ORM и какую проблему она решает?

ORM (Object-Relational Mapping) сопоставляет Python-классы и объекты с таблицами и строками реляционной БД. Вместо ручного составления SQL для каждой операции разработчик использует модели и сессии. Например, `Student` описывает структуру данных, а конкретный объект `Student(full_name="...", group_name="...")` представляет одну запись. В БД хранится строка таблицы `students`, а не сам Python-объект. Модель — определение в коде, таблица — физическая структура в базе, экземпляр модели — представление строки в памяти.

### 2. Чем внешний ключ отличается от Relationship?

`Grade.student_id` — целочисленный столбец таблицы `grades`, содержащий значение `students.id`. Ограничение внешнего ключа проверяет существование связанного студента. `Grade.student` — объектный атрибут ORM для доступа к экземпляру `Student`. Отдельного столбца `student` в SQL нет: ORM использует `student_id` и при необходимости выполняет запрос. Обратный атрибут `Student.grades` возвращает список связанных оценок.

### 3. Зачем нужен seeding?

Посев заполняет БД небольшим воспроизводимым набором примеров. На нем можно проверить связи, запросы и отображение данных. В пустой базе невозможно увидеть реальные результаты соединения таблиц и проверить, правильно ли предмет и оценка относятся к студенту. Повторяемый seed также позволяет быстро подготовить окружение для демонстрации.

### 4. Что делает echo=True?

Параметр включает вывод SQL-команд и параметров движка в журнал. При первом создании схемы видны `CREATE TABLE`, при посеве — `INSERT`, при чтении — `SELECT`. Это помогает проверить названия таблиц, порядок операций и причины ошибок. В рабочей системе подробное журналирование следует настраивать с учетом объема и содержимого данных.

### 5. Почему БД исключают из Git, а модели сохраняют?

Локальная БД — изменяемый бинарный файл с конкретными данными, в том числе потенциально персональными. Такие файлы плохо сравниваются и объединяются в Git и могут различаться у разработчиков. Модели и seed — текстовый код: его удобно проверять, версионировать и использовать для воспроизведения схемы и примеров. В `.gitignore` добавлены шаблоны для `*.db`, `*.sqlite3` и файлов журналов SQLite. Игнорирование не заменяет резервное копирование нужных данных.
